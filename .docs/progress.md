## M7：布局改版（已完成，经浏览器实测）

改版的出发点：调属性要滚的是操作区，演示区不该因此被滚出视野。

落地的东西：

- 宽屏（≥lg）整页锁死不滚——`App.vue` 根上 `lg:h-full` + `lg:overflow-hidden`，
  左侧操作区 `lg:overflow-y-auto` 自己滚，右列演示区吃满剩余高度。
  **窄屏不锁**：两栏塌成一栏后一屏放不下，锁死等于把下半页永久切掉，所以每条都带 `lg:` 前缀。
- 整页宽度封顶从 1440（`max-w-360`）提到 1920（`max-w-480`），多出来的宽度全部落给演示区。
  演示容器自身的拖拽上限 `STAGE_LIMITS.maxWidth` 保持 1200 未动——可视宽已达 1526，
  原本拖到 1200 要横向滚才看得全的容器现在完整放得下，收益已经拿到，再提上限反而重新超出可视区。
- 明细表与 CSS 输出合并进新的 `InspectorTabs.vue`，固定 208px 高、标签切换，
  默认停在明细（理论 vs 实际是本站的差异化核心，复制 CSS 是次要动作）。
  高度固定而不是自适应：行数随盒子增删变化，高度跟着跳会把演示区挤得忽大忽小。

  > 该组件已在 [M11](#m11三栏布局--icon-体系--shiki-高亮已完成经浏览器实测) 解散——
  > CSS 搬进独立右栏后标签条只剩一个标签。固定 208px 这个取舍仍然有效，由明细面板继承。

浏览器实测（窗口 `visibilityState: hidden`，全程以 DOM 读数为准，一张截图没用；
测量通道先用已知值自校验过——剩余空间实测 456px，与 `720 − 3×80 − 2×12` 精确吻合）：

| 验的是什么 | 实测 |
| --- | --- |
| 整页真的不滚 | `scrollHeight === clientHeight`，`scrollTo(0,500)` 后 `scrollY` 仍为 0 |
| 没有静默裁切 | header 0~76、grid 76~907、两列 92~891、检视面板 683~891，底部恰好剩 16px 的 `p-4`，溢出视口 0px |
| 操作区自己滚 | `scrollHeight 981 > clientHeight 797`，`scrollTop` 能到 184 |
| 演示区可视范围 | 1526×521（原来约 1040 宽），容器拖到上限 1200 宽也完整放得下，不再横向滚 |
| 面板高度不随容器晃 | 容器 1200×600 与 600×120 两态下，演示面板恒 575、滚动容器恒 521 |
| 标签切换 | 切 CSS：代码出现、明细卸载、面板恒 208；切回明细：3 行俱在 |
| 顶面没被裁 | 滚动容器 `padding-top: 12px`，stage 顶边到内容顶实测 12 ≥ `blockDepth` 10 |

> ⚠️ `overflow: hidden` 会把溢出**藏起来**而不是报出来，所以「页面不滚」本身证明不了「装得下」。
> 结论是靠量每一层的 `top` / `bottom` 与视口边界的关系得出的，不是靠「没看见滚动条」。

排查中值得记一笔的假警报：演示区可视高先读到 577、后读到 521。真因是视口高从 963 变成 907
（窗口自己变了），`963 − 907 = 56` 与差值精确吻合，**不是布局随容器尺寸晃动**——
两种容器尺寸下各量一遍，面板高度恒定。

## M8：间距统一与控制面板收敛（已完成，经浏览器实测）

三件事一起做的，但根子是同一个。

**① 全站只留两档间距**，提成 CSS 变量并映射成 UnoCSS 工具类
（`--space: 12px` → `p-space` / `gap-space`，`--space-tight: 4px` → `gap-tight`）。

真正的病根不是取值有四档（16 / 16 / 12 / 20），而是 **margin 与 gap 混用**：
字段各自带 `mb-3`，外层再叠一层 `gap-5`，边界处就是两份相加。
肉眼看到的「分节之间远宽于字段之间」不是设计意图，是这份叠加的副产物。
现在子元素一律不带 margin，竖向节奏全部由父级的 `gap` 承担。
左上角标题也是同一个病：`header` 的下内边距加上栅格的上内边距叠成 32，而上方只有 16——
现在 `header` 只给上内边距，下方留白交给栅格，上下都是 12。

**② 「更多值」折叠区整个拆掉**，每个枚举属性的取值一次全摆出来。
`justify-content` 从 6 个值变成 10 个，`align-items` 从 5 个变成 9 个。
拆的时候发现 `ItemControls` 那侧的 `showAdvanced` 恒为 `false` 且从来没渲染过开关——
**盒子属性的折叠值一直是够不着的死功能**。
定稿设计文档 [2026-09-08-todo-flex-design.md](./superpowers/specs/2026-09-08-todo-flex-design.md)
第 8.1 节原本写着「规范全集放折叠区」，已就地标注移除，免得下个会话照着文档把它加回来。

**③ 操作区所有可点控件的上下内边距统一到 `--space-tight`**
（选项按钮原本 3px、简写按钮 2px、列表行与文本框 4px）。

浏览器实测（`visibilityState: hidden`，全程 DOM 与 computed style，未用截图；
测量通道先用已知值自校验——剩余空间实测 456px，与理论值精确吻合）：

| 量的是什么 | 实测 |
| --- | --- |
| 标题块上下 | 上 12 / 下 12（改前 上 16 / 下 32） |
| 模块内边距 | 栅格、操作区、演示区面板、演示区滚动容器、检视面板内容区全部 12px，栅格列距 12px |
| 操作区分节之间 | 12 / 12 / 12 |
| 分节内字段之间 | 八个间隔全是 12 |
| 盒子属性那一节 | 九个间隔去重后只剩一个值：12 |
| 标签 → 控件 | 4 |
| 可点控件上下内边距 | 选项按钮 4/4、列表行 4/4 |
| 原折叠值 | `start` / `end` / `left` / `right` / `first baseline` / `last baseline` / `self-start` / `self-end` 首屏 8/8 可见 |
| 原折叠值真能用 | 点 `left` → 选中态 + 导出 CSS 出现 `justify-content: left` + 地址栏短码同步 |

### 新守卫「模块间距只走变量」自己先瞎了两次

`ThePlayground.spec.ts` 新增了一条读源码的守卫，禁止模板里出现硬编码的
`gap-4` / `mb-2` 这类数值间距类。它一开始**看着是绿的，其实基本失明**，
靠往九个组件逐个塞违规类做变异验证才查出两个 bug：

1. `for (const [cls] of str.matchAll(/class="([^"]*)"/g))` 解构的是**整段匹配**
   （带着 `class="` 和收尾引号），不是捕获组。于是只有夹在中间的类名能被认出来，
   **首尾两个永远漏检**。它当初逮到了 `PropertyField` 里夹在中间的一个 `gap-2`，
   这个「有产出」的假象正好掩护它蒙混过关。
2. 提取模板用的非贪婪 `<template>([\s\S]*?)</template>` 在 `ItemControls.vue` 的
   `<template v-else>` 处提前收尾，那之后的模板一行都扫不到。改成贪婪匹配到最后一个
   `</template>` 才对。

修完后九个组件 9/9 全部命中。
**教训：读源码的守卫测试必须先做变异验证再信它**——它不像行为测试那样会因为实现缺失而自然变红，
写错了也照样全绿，而一条绿着的瞎守卫比没有守卫更危险。

## M9：滚动条、悬停余量、叠加层层序（已完成，经浏览器实测）

**① 全局滚动条对齐 Element Plus 的 `el-scrollbar` 外观**
（6px、4px 圆角、轨道透明、滑块 `#909399` 30% → 悬停 50%，取值就是 el 的
`--el-scrollbar-bg-color` 配 `--el-scrollbar-opacity`）。这组中性灰在两套主题下都立得住，不分主题。
无法消除的差别只有一处：el-scrollbar 是 JS 画的悬浮层不占布局，这里是原生伪元素，占 6px 宽。

> ⚠️ **第一版在浏览器里是失效的，而且失效得很安静。**
> 原写法把 `scrollbar-width: thin` 加在 `*` 上——Chrome 一旦见到标准属性，
> 就**整个忽略 `::-webkit-scrollbar` 的样式**，滚动条退回自带的 thin 造型，实测只占 2px。
> 规则全都在构建产物里，grep 得到、单测也没话说，只有真实渲染量得出来。
> 现在用 `@supports not selector(::-webkit-scrollbar)` 把标准属性隔离给 Firefox。
> **这条没有自动化守卫兜底**（纯外观，没有可断言的不变量），改动它之后必须去浏览器量一次
> `offsetWidth - clientWidth - 左右边框`。

**② 悬停时方块不再被裁**。伸出量是三项叠加，实测：顶面 `blockDepth × blockDepthHover` = 13px、
抬升 `liftHeight` = 6px、`liftScale` 放大单边最多 18px（横）/ 9px（纵）。
余量做成 `motion.stageOverhang`（32px）下发成 `--overhang`，落在 `.stage-wrapper` 的**外边距**上。

> 为什么是外边距不是内边距：叠加层相对 `.stage-wrapper` 绝对定位，
> wrapper 一有内边距，叠加层的 `top/left: 0` 就对到内边距盒而不是 `.stage` 的左上角，整层错位。

实测余量（**只看上/左**：`scrollTop`/`scrollLeft` 不能为负，往这两个方向溢出的像素永远滚不到，
而右/下溢出滚一下就有）：

| 场景 | 上 | 左 |
| --- | --- | --- |
| 默认 720×320、三盒 | 20 | 43 |
| 上限 1200×600、三盒 | 16 | — |
| 最坏：单盒 `flex: 1` 撑满 1200×600 | 16 | 26 |

**③ 叠加层沉到盒子下方**，读起来像「铺在台面上、被方块压住」的一层。
实测层序：色块层 `0` < 盒子 `1` < HUD 层 `2` = 手柄 `2`。
并且核对过中间的 `.stage` 与 `.stage-wrapper`——`z-index / transform / opacity / filter /
isolation / contain / will-change / mix-blend-mode` 全是中性值，
**没有谁偷偷开出新的层叠上下文**，所以这三个数字是直接可比的，绘制顺序是确定的而非碰巧。

> **HUD 没有跟着沉下去，是故意的。** 它是标签，沉下去就会被它要标注的那个盒子挡住——
> 盒子贴容器顶时 HUD 本来就要翻到盒子内侧，那一翻正好翻到盒子底下。所以拆成两层。

### 两个新的测量坑（已进 browser-verification.md）

1. `el.style.cssText = ''` 会把 Vue 的 `:style` 绑定一起抹掉。文档原本教「量真实布局前把 Flip 的
   内联样式清掉」，照做的结果是量出一个假结论：列表行写着 `flex: 1 1 0`、computed 却是 `0 1 auto`、
   本该 1200px 的盒子只有 80px。**状态与渲染对不上时，先怀疑是不是自己刚把绑定清了。**
2. 探针里写 `while (按钮数 > 1) 点一下` 会死循环——Vue 的 DOM 更新是异步的，重查到的还是旧节点，
   直接卡死渲染进程、CDP 45 秒超时，看起来像扩展挂了。重载标签页即可恢复。

### 窄屏那条踩了两次：第一次连诊断都是错的

用户拖窄窗口报「CSS 模块消失」。**第一版诊断完全错了**，值得原样记下来：

> 当时的推断是：CSS 面板滚动层写成无前缀的 `min-h-0 flex-1`，窄屏下面板高度由内容决定，
> `flex: 1 1 0%` 配上显式 `min-height: 0` 让假设主尺寸算成 0，被 `overflow-hidden` 裁掉。
> 据此加了 `lg:` 前缀并补了一条反向守卫，全绿，提交推送。

**那次没有在浏览器里复现过缺陷本身**——只验了「修完是好的」，没验「不修是坏的」。
下一轮补验时把修复退回去，在窄屏模拟下代码块**仍然是 390px，根本没塌**：
诊断是假的，守卫钉的是一条不存在的规律，而它照样全绿。

真正的机制是另一回事，靠 `resize_window` 到 1100px 量出来的：

| 量到的 | 值 |
| --- | --- |
| `grid-template-columns` | `320px 834px 320px`（合计 1498px） |
| grid 实际宽度 | 1100px |
| CSS 栏矩形 | `left: 1190, right: 1510` —— 整块在视口之外 |
| `documentElement.scrollWidth` | 1100 —— **横向滚不到，被 `lg:overflow-hidden` 裁掉了** |

`1fr` 等价于 `minmax(auto, 1fr)`，那个 auto 下限取的是该列的 min-content。
逐层量下来，撑住它的是**演示区滚动层的 808px**（`.stage` 固定 720px 加两侧内边距）——
它自己的 `overflow-auto` 只挡得住自己溢出，**挡不住 min-content 往上冒到 grid 轨道**。
于是 lg 到约 1500px 之间的每个宽度，右栏都被顶出视口。

修法是两半，缺一不可：轨道写 `minmax(0, 1fr)`，`<main>` 加 `lg:min-w-0`
（轨道让开了，grid 项自己的自动最小尺寸仍会把它撑到 min-content）。
修完三个宽度实测：1024px → `320px 336px 320px`、1100px → `320px 412px 320px`、
1920px → `320px 1232px 320px`（与修复前逐像素一致），CSS 栏在每个宽度都完整落在视口内，
演示区改为内部横向滚动而 `.stage` 仍是真实的 720px。

**768px 以下由人眼补验通过**（本机 `resize_window` 压不到那里，自动化到 900px 为止）。
至此窄屏这条核对完毕（清单里的第 8 条）。

**这一条要记住的不是 grid 的规则，是流程**：
「改完跑绿」不等于「诊断成立」。**守卫写完必须让它见一次真实的红**——
不只是把代码改坏让它红，而是确认**当初那个缺陷现场**能让它红。

### 变异脚本自己也骗过一次

补验时有两条变异「全绿」，一度读成守卫是瞎的。实际是 perl 替换打偏了目标：
`lg:min-w-0` 在文件里出现两次（注释里也提到它），替换掉的是注释那处，`<main>` 的 class 没动。

**变异没落地却被读成「守卫是瞎的」，和被读成「守卫没问题」同样危险**——
前者会让人去改一条本来正确的守卫。脚本现在每次变异后跑一次 `cmp`，自报文件到底改没改。

### 变异验证记录

值得单独记一笔的是对比度守卫那组：除了「换回 vitesse」「单主题输出」之外，
还故意把 `--panel` 的暗色值改亮到与 token 撞色，确认也变红——

## 已由浏览器核对排除的三条

2026-09-18 用 DOM 与 computed style 核对（**不靠截图**：窗口 `visibilityState` 当时是 `hidden`，
截图拿到的是陈旧帧）。测量通道用已知理论值自校验过——默认状态剩余空间实测 456px，
与 `720 − 3×80 − 2×12` 精确吻合，说明布局读数可信。

- **column 下三盒宽度递减**——已排除。三盒均 720，`stretch` 正常。
  632 / 542 / 422 确认是冻帧假象，别再查。
- **wrap 换行时跨行的面互压**——不互压。默认 gap=12 下，第一行底边 154、第二行顶面顶点 156，余量 2px。
  `--d` 的公式正是为此设计的，见下面那条。
- **`align-items: stretch` 时顶面画到容器外**——**查出真缺陷并已修**：顶面上沿 2px 被外层
  `.overflow-auto` 裁掉（那层 padding 只有 8px，装不下 10px 的顶面）。已把 padding 提到 12px，
  `ThePlayground.spec.ts` 加了守卫钉住 `padding ≥ motion.blockDepth`。详见
  [pitfalls.md](./pitfalls.md#滚动容器的内边距必须容得下伸出去的面)。

### 顺带查清的两件事

**`--d` 的真实公式**是 `Math.max(3, Math.min(10, min(rowGap, columnGap) - 2))`，
带下限 3 和上限 10 的双向钳制，不是单纯的 `min(gap) - 2`。
`gap < 5` 时下限生效，厚度会大于间距：

| gap | 0 | 1 | 2 | 3 | 4 | ≥5 |
| --- | --- | --- | --- | --- | --- | --- |
| `--d` | 3 | 3 | 3 | 3 | 3 | gap−2 |
| 间距余量 | −3 | −2 | −1 | 0 | 1 | 2 |

**余量为负不是缺陷**。等距投影里靠下即靠前，第二行本就该遮住第一行的底部——
就像两块实体紧贴时前面那块会挡住后面那块。实测两行的 `.stage-box` 同为
`position: relative` + `z-index: auto` 且在同一层叠上下文，按 CSS 绘制顺序 DOM 靠后者在上，
第二行正好压在第一行上，**遮挡方向是对的**。
计划文档里「留 2px 余量」的措辞容易让人把这读成 bug 来"修"，实际它只影响
「两块看起来分不分离」，而 gap 小的时候它们本来就该看起来紧贴。

> ⚠️ 命中测试（`elementFromPoint`）验证不了这个：伪元素不参与命中测试，
> 探测点会穿透到下方的宿主元素上，读出来的归属是反的。只能按 CSS 绘制规则判断。
